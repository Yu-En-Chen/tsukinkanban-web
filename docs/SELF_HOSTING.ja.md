# 通勤看板 フロントエンド：セルフホスティングガイド兼バックエンド API 仕様

日本語 | [繁體中文](SELF_HOSTING.md)

本書は、このフロントエンドを使って自分でサイトを運用したい方に向けた説明書です。

このリポジトリに含まれるのはフロントエンド（静的な Web ページ）だけで、**バックエンドは含まれていません**。リアルタイムのデータはすべて 1 台の API サーバーから取得しており、フロントエンドの中に API キーなどの秘密情報はありません。サイトを動かすには、次の作業が必要です。

1. このリポジトリを静的サイトとして任意のホスティングに配置する（ビルド工程は不要です）。
2. バックエンドを自分で用意し、本書の第 4～9 章に記載した 10 個のエンドポイントを実装する。
3. フロントエンドに直接書かれている API の URL を、自分のバックエンドのものに書き換える（第 2 章）。
4. サイト名や連絡先などのブランド情報を差し替える（第 2 章）。

本書の内容は、フロントエンドのソースコードを基準にしています（対象：`main` ブランチの `69d4ccc`）。フロントエンドからは読み取れないバックエンド内部の処理は、第 13 章に「バックエンド側で補足が必要な事項」としてまとめています。

## 1. 全体構成

### 1.1 フロントエンド

- HTML / CSS / JavaScript（ES Modules）だけで作られています。フレームワーク、外部モジュール、ビルド工程はありません。
- ローカルで動かすには、リポジトリのルートで `python3 -m http.server 8000` を実行し、`http://localhost:8000` を開きます。
- 本番サイトは現在 GitHub Pages で配信しています。静的ファイルを配信できるホスティングであれば、どこでも動作します。
- 利用者のカードと設定はブラウザの中だけに保存されます（IndexedDB。使えない環境では localStorage）。サーバーには送信されません。

<!-- 表: 主なファイル -->

| パス | 内容 |
|---|---|
| `index.html` | 唯一のページ（アプリシェル） |
| `manifest.json` | PWA の設定 |
| `js/script.js` | メインの処理：カード、ランプ、検索、鉄道の運行状況 |
| `js/flights.js` | フライト |
| `js/buses.js`、`js/bus-timetable.js` | バス、停留所の時刻表 |
| `js/ship.js` | 船 |
| `js/history-daemon.js`、`js/menu.js` | 履歴の取得と表示 |
| `js/data-sources.js` | データ提供状況（提供終了の案内） |
| `js/clock.js` | 左上の同期時計。1 分ごとの更新のきっかけにもなっています |
| `data/db.js`、`data/dictionary-db.js` | ブラウザ内のデータベース |
| `data/data.js` | 初期状態の 5 枚のカード |
| `data/route-id-migration.js` | 路線 ID の変更対応表 |
| `data/about.js`、`terms.js`、`data-source.js`、`supporter.js` | メニュー内の説明ページの内容 |

### 1.2 フロントエンドが呼び出すエンドポイント

すべて `GET` で、認証情報は付けません。現在のホストは `https://api.tsukinkanban.com` です。

<!-- 表: エンドポイント一覧 -->

| エンドポイント | 用途 | 呼び出すタイミング |
|---|---|---|
| `/api/dictionary` | 鉄道の路線辞書 | サイトを開いたときに 1 回 |
| `/api/status` | 鉄道の運行状況 | 開いたとき、その後 1 分ごと、バックグラウンドから戻ったとき |
| `/api/flights` | フライト一覧 | 開いてから 1.5 秒後。その後は `/api/status` と一緒に 1 分ごと |
| `/api/bus/routes?q={キーワード}` | バスの路線名検索 | 2 文字以上を検索し、入力が 250 ミリ秒止まったとき |
| `/api/bus/stop/{停留所名}` | 停留所の到着情報 | 検索時。停留所パネルを開いている間は 55 秒ごと |
| `/api/bus/route/{路線名}` | バス路線の詳細 | 路線を開いたとき。カードにバス路線がある間は 55 秒ごと |
| `/api/bus/timetable/{停留所名}` | 停留所の終日の時刻表 | 時刻表ページを開いたときに 1 回（同じ停留所は 30 分間再取得しません） |
| `/api/ship/schedule?date=YYYY-MM-DD` | 船の便と運航状況 | カードに航路があるとき、船のページを開いたとき、船に関する語を検索したとき。当日分は 5 分ごと |
| `/api/history/all` | 鉄道・フライト・船の履歴 | 60 秒ごと |
| `/api/sources` | データ提供状況 | サイトを開いたときに 1 回 |

バスと船は、「利用者が検索したとき」または「カードに登録されているとき」だけリクエストを送ります。それ以外のときは呼び出しません。

### 1.3 共通の取り決め

- **形式**：レスポンスはすべて UTF-8 の JSON です。
- **CORS**：フロントエンドは自分のドメインから直接 API を呼び出します。バックエンドは `Access-Control-Allow-Origin` で自分のサイトのドメインを許可してください。リクエストに独自ヘッダーはないため、プリフライトは発生しません。
- **エラー**：バックエンドの初期化中、バス・船・時刻表のエンドポイントは HTTP 200 で `{ "error": "メッセージ" }` を返します。フロントエンドはメッセージを表示するか、少し待って再試行します。`/api/status` の扱いは第 4.5 節を参照してください。
- **時刻**：ISO 8601 形式で `+09:00` を付けます。名前が `_text` で終わる項目は、そのまま表示できる `HH:MM` です。停留所の時刻表と船のページでは、日付と「次の便」の計算をすべて日本時間で行い、端末のタイムゾーンは使いません。
- **キャッシュ**：`/api/status`、`/api/flights`、`/api/bus/*`（時刻表を除く）は、フロントエンドが `cache: 'no-store'` を指定して取得します。それ以外はブラウザの既定の動作なので、CDN でキャッシュできます。`/api/history/all` はあえてパラメーターを付けておらず、現在は CDN の 1 分間のキャッシュを利用しています。

> **注意**　バスの路線名、事業者 ID、航路名、鉄道の路線 ID は、そのまま利用者のカードに保存されます。バックエンド側で名前を変えると、保存済みのカードが使えなくなります（鉄道だけは救済の仕組みがあります。第 3.3 節）。

## 3. 路線IDとカードのルール

### 3.1 ID の形式でカードの種類が決まる

フロントエンドは ID の文字列の形だけで種類を見分けます。バックエンドの ID は次の表に従ってください。

<!-- 表: ID の形式 -->

| 種類 | ID の形式 | 例 |
|---|---|---|
| 鉄道 | 任意の文字列。**`.` または `:` を必ず含み**、`bus:`、`ship:` で始まらないこと | `odpt.Railway:JR-East.Yamanote` |
| バス | `bus:{事業者 ID}:{路線名}`（路線名は半角） | `bus:Toei:都01` |
| 航路 | `ship:{航路名}` | `ship:東京～三宅島・御蔵島・八丈島航路` |
| フライト | 便名。**`.` と `:` を含まないこと** | `JL123` |

カードの先頭の ID が `.` も `:` も含まない場合、そのカード全体がフライトのカードとして扱われます。

### 3.2 カードの制限

- 画面に表示できるカードは最大 5 枚です。このほかに最大 5 枚を非表示にできます。
- 1 枚のカードに登録できる路線は最大 6 つです。鉄道、バス、航路は同じカードに混在できます。
- フライトは 1 枚のカードに 1 便だけで、ほかの種類と混在できません。
- エクスポートの形式は配列です：`[{ "name": "カード名", "hex": "#009100", "routes": ["ID", …] }]`。カラーだけをエクスポートした場合は `["#009100", …]` です。インポート時のカード名は 40 文字までです。

### 3.3 鉄道路線 ID の変更

`data/route-id-migration.js` に「旧 ID → 新 ID」の対応表があります。フロントエンドは設定を読み込むたびに、新しい ID が `/api/dictionary` または `/api/status` にすでに存在する場合に限って、利用者のカードの旧 ID を新 ID に置き換えます。このため、フロントエンドを先に公開し、あとからバックエンドの ID を切り替えることができます。自分でサイトを運用する場合、この表は空にして構いません。

### 3.4 7 つのランプ

カードの右上には 7 つのランプがあり、プログラム上は真偽値の配列です。

<!-- 表: ランプの一覧 -->

| 位置 | 記号 | 意味 |
|---|---|---|
| 0 | 地震 | メッセージに「地震」が含まれる |
| 1 | 雨風 | メッセージに「雨」または「台風」が含まれる |
| 2 | 雪 | メッセージに「雪」が含まれる |
| 3 | × | 大幅な遅れ、運休、欠航、エラー、本日の便がない |
| 4 | △ | 遅れ、条件付き運航など |
| 5 | 〇 | 平常 |
| 6 | 吹き出し | お知らせがある、情報を確認中、実際の状況を確認できない |

## 4. 鉄道（2つのモード）

鉄道では 2 つのエンドポイントを使います。路線辞書（どの路線があるか）と運行状況（いまどうなっているか）です。

### 4.1 `GET /api/dictionary`

```jsonc
{
  "version": "c8080d4ba3bc",
  "routes": {
    "odpt.Railway:JR-East.Yamanote": {
      "name": "山手線",
      "company": "JR東日本",
      "kana": "やまのてせん",
      "en": "Yamanote",
      "hex": "#9acd32",
      "url": "https://www.jreast.co.jp/"
    }
  }
}
```

<!-- 表: /api/dictionary の項目 -->

| 項目 | 必須 | 説明 |
|---|---|---|
| `version` | ○ | 任意の文字列です。フロントエンドは辞書をブラウザに保存し、**`version` が前回と異なるときだけ再取得します**。内容を変えたら必ずバージョンも変えてください |
| `routes` | ○ | 路線 ID をキーにしたオブジェクト |
| `name` | ○ | 路線名。検索結果は路線名で重複を除くため、**別の路線に同じ名前を付けないでください** |
| `company` | ○ | 事業者名 |
| `kana`、`en` | － | 検索の照合にだけ使います |
| `hex` | － | 路線カラー。検索のプレビューカードに使います。ない場合は濃い灰色になります |
| `url` | － | 事業者の公式サイト。カード右上の外部リンクのメニューに表示します |

検索はすべてフロントエンド側で行います。`name`、`company`、`kana`、`en` を、小文字にして空白と `-` を除いたうえで照合します。

### 4.2 `GET /api/status`

路線 ID をキーにしたオブジェクトで、このほかに `_meta` があります。

```jsonc
{
  "_meta": { "server_time": "2026-10-21T10:00:00+09:00" },

  // モード A：運行情報（文章）だけ
  "odpt.Railway:TokyoMetro.Ginza": {
    "status_type": "取得済",
    "status_text": "平常運転",
    "message": "平常どおり運転しています",
    "delay_minutes": 0,
    "update_time": "10:00"
  },

  // モード B：遅延分数あり（列車ロケーション情報から算出）
  "odpt.Railway:JR-East.Yamanote": {
    "status_type": "取得済",
    "status_text": "平常運転",
    "message": "平常どおり運転しています",
    "delay_minutes": 8,
    "update_time": "10:00",
    "advanced_details": [
      { "direction_name": "内回り", "max_delay": 8, "train_count": 3 },
      { "direction_name": "外回り", "max_delay": 2, "train_count": 0 }
    ]
  }
}
```

<!-- 表: /api/status の項目 -->

| 項目 | 必須 | 説明 |
|---|---|---|
| `_meta.server_time` | － | 左上の同期時計に表示します。ない場合は端末の時刻を使います |
| `status_type` | ○ | 状態の種類。第 4.4 節を参照 |
| `status_text` | ○ | 状態を表す短い文字列。空文字列でも構いません |
| `message` | ○ | 路線カードに表示する説明文。ランプの判定にも使います（第 4.4 節） |
| `delay_minutes` | － | その路線の現在の遅延分数。ない場合と 0 は「分数のデータなし」として扱います |
| `update_time` | ○ | `HH:MM`。`--:--` と空文字列は `--:--` と表示し、`----` と `本日公式発表なし` は「公式発表なし」と表示します |
| `advanced_details` | － | 方面別の遅れ。第 4.3 節を参照 |
| `url` | － | 公式サイト。状態が「提供終了」のときにリンクとして表示します。ない場合は辞書の `url` を使います |

> **注意**　`status_text` は必ず文字列で返してください。省略すると、メッセージが平常の内容でないときにフロントエンドでエラーになります。

### 4.3 2 つのモード

フロントエンドは事業者を区別せず、項目に値があるかどうかだけを見ます。

<!-- 表: 鉄道の 2 つのモード -->

| | モード A：運行情報 | モード B：遅延分数 |
|---|---|---|
| データの元 | 事業者が発表する運行情報（文章） | バックエンドが列車ロケーション情報から算出した遅れ |
| 項目 | `status_type`、`status_text`、`message` | これに加えて `delay_minutes`、`advanced_details` |
| ランプの根拠 | 文章中のキーワード | 分数（文章より優先） |
| 現在の対象 | すべての路線 | JR 東日本、東武鉄道、都営地下鉄、横浜市営地下鉄 |

`advanced_details` の 1 件が 1 つの方面です。

<!-- 表: advanced_details の項目 -->

| 項目 | 説明 |
|---|---|
| `direction_name` | 方面名。そのまま表示します。行き先の分かる書き方をおすすめします（例：「大宮・上野・東京方面」） |
| `max_delay` | その方面の最大の遅延分数。5 以下は「平常」、6～15 は黄色、16 以上は赤で表示します |
| `train_count` | 列車の本数。0 より大きいときに「(N列車)」と表示します |

方面名の付け方や、直通列車（湘南新宿ライン、上野東京ライン）の集計方法はバックエンドの役割です。フロントエンドは表示するだけです。

### 4.4 フロントエンドのランプ判定

路線ごとに次の順で判定し、当てはまったところで終わります。

<!-- 表: 鉄道のランプ判定の順序 -->

| 順序 | 条件 | 結果 |
|---|---|---|
| 1 | `status_type` が `通信エラー` | 吹き出し（赤は点けません） |
| 2 | `status_type` に「エラー」が含まれる | × |
| 3 | `status_type` が `非対応`、`対象外`、`提供終了`、`更新中...` のいずれか。または `status_text` が `公式発表なし`、`情報なし` | 吹き出しだけ（〇は点けません） |
| 4 | `delay_minutes` が 0 より大きい | 5 以下は 〇、6～15 は △、16 以上は × |
| 5 | メッセージが平常の内容ではなく、かつ `status_text` に「異常」、`message` に「遅延」、`status_type` に「見合わせ」「運転変更」のいずれかが含まれる | △ |
| 6 | その他 | 〇 |

- **平常のメッセージ**：`message` に「ありません」「平常」「正常」「取得しています」のいずれかが含まれるもの。
- **吹き出しがほかに点く場合**：`message` に内容があり平常のメッセージではないとき。または `status_type`、`message` に「お知らせ」が含まれるとき。
- **天候のランプ**：`message` に「地震」「雨」「台風」「雪」が含まれるとき。

カードのランプは、カード内のすべての路線の結果を合わせたものです。

### 4.5 特別な状態

<!-- 表: status_type の値 -->

| `status_type` | 意味 | フロントエンドの表示 |
|---|---|---|
| `取得済` | 正常に取得できた | 第 4.4 節のとおり |
| `通信エラー` | バックエンドが上流から取得できなかった | 吹き出し |
| `対象外` | 上流がこの路線のデータを提供していない | 吹き出し |
| `提供終了` | データの提供期間が終了した | 灰色の情報アイコン付きのバッジ。`message` と `url` のリンクを表示し、`advanced_details` は表示しません |

`/api/status` 自体に問題があるときの動作は次のとおりです。

<!-- 表: /api/status に問題があるときの動作 -->

| 状況 | フロントエンドの動作 |
|---|---|
| サイトを開いたときに接続できない（2xx 以外、または通信エラー） | すべての鉄道路線を「通信エラー」と表示します |
| 1 分ごとの更新で接続できない | それまでの画面を残します |
| レスポンスの最上位に `error` がある | その回の更新を行いません |
| レスポンスが `{}`（バックエンドの起動直後） | 同期時計を更新せず、路線を「更新中...」（吹き出し）と表示します |
| レスポンスに該当の路線がない | その路線を「更新中...」（吹き出し）と表示します |

左上の同期時計は、最後に同期できてから 1 分以上で黄色、5 分以上で赤になります。

### 5.1 `GET /api/flights`

配列を返します。1 件が 1 つの便です。

```jsonc
[
  {
    "fid": ["UO625", "CX5625"],
    "airline": "香港エクスプレス",
    "type": "Departure",
    "airport": "羽田（HND）",
    "location": "香港（HKG）",

    "status": "搭乗手続中",
    "terminal": "3",
    "gate": "105",
    "note": "",
    "system_updated": "05:48:06",
    "stale": false
  }
]
```

<!-- 表: /api/flights の項目 -->

| 項目 | 必須 | 説明 |
|---|---|---|
| `fid` | ○ | **配列**です。先頭が実際に運航する便名、2 番目以降が共同運航便名です。利用者はどの便名でも検索できます |
| `airline` | ○ | 航空会社名。そのまま表示します。カラーと公式サイトの照合にも使います |
| `type` | ○ | `Departure`（出発）または `Arrival`（到着） |
| `airport` | ○ | 東京側の空港。`HND`、`NRT` のほか、`羽田（HND）` のような書き方でも構いません。フロントエンドが 3 文字のコードを取り出します |
| `location` | ○ | 相手側の空港。例：`札幌（CTS）`。フロントエンドは `CTS（札幌）` と表示します |
| `scheduled` | ○ | 定刻 `HH:MM`。ない場合は `--:--`。**必ず文字列**で返してください |
| `latest` | ○ | 最新の時刻。形式は同じです。`scheduled` と異なるときに「変更」と差の分数を表示します |
| `status` | ○ | 状態。第 5.2 節を参照 |
| `terminal` | － | ターミナル。ない場合は `---` または空文字列 |
| `gate` | － | 搭乗口。ない場合は `---` または空文字列 |
| `note` | － | 備考。内容があると吹き出しが点き、カードの下に表示します |
| `system_updated` | － | そのデータの更新時刻 `HH:MM:SS`。フロントエンドは先頭の 5 文字を表示します |
| `stale` | － | `true` は、上流の更新が一定時間止まっていることを表します（現在のバックエンドの基準は 15 分）。フロントエンドは「⚠ 情報が古い可能性があります」と表示します |

利用者が保存するフライトの ID は便名です。一覧から便がなくなると（運航が終わった、またはバックエンドにデータがない）、カードに「フライト情報が終了したか、取得できません」と表示します。

### 5.2 `status` の値

フロントエンドは英語のコード（日本語に変換します）と日本語のどちらも受け付けます。

<!-- 表: status の英語コードと表示 -->

| 英語のコード | 表示 | 英語のコード | 表示 |
|---|---|---|---|
| `Normal` | 通常 | `NowBoarding` | 搭乗中 |
| `Delayed` | 遅延 | `FinalCall` | 最終案内 |
| `Cancelled` | 欠航 | `GateClosed` | 搭乗終了 |
| `EstimatedDeparture` | 出発予定 | `GoToGate` | 搭乗口へ |
| `EstimatedArrival` | 到着予定 | `LeftGate` | 滑行中 |
| `Estimated` | 変更予定 | `InAir` | 飛行中 |
| `CheckIn` | 搭乗手続中 | `Takeoff`、`Departed` | 出発済 |
| `NewArrival` | 新規到着 | `Landed`、`Arrived` | 着陸済、到着済 |

表にない値は、そのまま黄色で表示します。

ランプは次の順で判定します。

1. 「欠航」は ×。
2. 「出発済」「着陸済」「到着済」「飛行中」は 〇。
3. `latest` が `scheduled` より 15 分を超えて遅い、または 20 分を超えて早い場合は △。
4. 状態が「遅延」で、時刻に変更がない場合は △。
5. その他は 〇。

このほか、`latest` と `scheduled` の差が 25 分を超えていて状態が「通常」「出発予定」「到着予定」のままの場合、フロントエンドは表示を「遅延」（遅い場合）または「変更予定」（早い場合）に変えます。

### 5.3 ターミナルと搭乗口

- `terminal` と `gate` をそのまま表示します。フロントエンドは問い合わせや推測を行いません。
- 表示するのは東京側の空港の情報だけです。出発便は「出発」の欄、到着便は「到着」の欄に表示し、相手側は `-` と表示します。
- 値が空文字列または `---` のときは `-` と表示します。

### 5.4 Google マップへのリンク

**キーワード検索の URL を使います。Google Maps API は使わず、API キーも不要です。**

```
https://www.google.com/maps/search/?api=1&query={キーワード}
```

キーワードはフロントエンドで組み立てます。

<!-- 表: Google マップの検索キーワード -->

| 条件 | キーワード |
|---|---|
| `airport` が HND | `羽田空港` |
| `airport` が NRT | `成田空港` |
| `terminal` がある | 後ろに ` {terminal}ターミナル` を付けます（値に「ターミナル」が含まれている場合は付けません）。例：`羽田空港 3ターミナル` |
| その他の空港 | リンクを出しません |

このため、`terminal` は「1」「2」「3」のような値で返してください。Google マップが該当するターミナルを見つけられます。

バスの停留所も同じ方法で、キーワードは `{停留所名} バス停` です。

停留所の終日の時刻表（平日・土曜・休日）です。

```jsonc

  "results": [

      "operator": "Toei", "label": "都営バス", "url": "…",
      "updated": {
        "data_date": "2026-10-02T03:00:00+09:00",

        {
          "name": "渋谷駅前",
          "poles": [
            {
              "pole_no": "1",
              "routes": [
                {
                  "route": "都０１",
                  "destination": "新橋駅前行",
                  "timetable": {
                    "weekday": [
                      { "hour": 6, "minutes": ["05", "25"] },
                      { "hour": 24, "minutes": ["10"] }
                    ],
                    "saturday": [ { "hour": 6, "minutes": ["05", "30"] } ],
                    "holiday": []
                  },
                  "count": { "weekday": 3, "saturday": 2, "holiday": 0 }
                }
              ]
            }
          ]
        }
      ]
    }
  ]
}
```

<!-- 表: /api/bus/timetable の項目 -->

| 項目 | 説明 |
|---|---|
| `today` | 今日の日別：`weekday`、`saturday`、`holiday`。フロントエンドは最初にこのタブを開きます。午前 4 時より前は前日として扱います |
| `results[].today` | 任意。事業者ごとの日別（祝日を判定済み）。ある場合はこちらを優先します |
| `timetable.{日別}` | 時の順に並べた配列。`minutes` は 2 桁の文字列です。空の配列は、その日別に便がないことを表します |
| `hour` | 4～27。24 以上は深夜の便で、フロントエンドは「24」「25」とそのまま表示します |
| `count` | 日別ごとの便数 |
| `pole_no` | 値がある場合に「N番のりば」と表示します |
| `matched` | 一致した停留所の数。`stops` の件数より大きい場合、フロントエンドは「候補が多すぎます」と案内します |
| `updated` | `effective_from`（改正日）、`data_date`、`fetched_at`、`valid_to`（有効期限）、`expired`。`expired: true` のときは、有効期限が切れている旨を表示します |
| `note`、`active_today`、`ship_link` | 時刻表のみの事業者だけにあります |

フロントエンド側の処理は次のとおりです。

- タイムアウトは 60 秒です（ある停留所が初めて問い合わせられたとき、現在のバックエンドはその場でデータを取得します）。
- `error` を受け取った場合は、5 秒後に自動で再試行します。
- 「次の便」はフロントエンドが日本時間で計算し、1 分ごとに計算し直します。API は再取得しません。

### 6.6 時刻表のみの事業者

結果に `realtime: false` がある場合、フロントエンドは次のように動作します。

<!-- 表: 時刻表のみの事業者の表示 -->

| 項目 | 動作 |
|---|---|
| 到着予測、車両、遅れ | 表示しません（`eta` は `null`、`buses_approaching` は空の配列にしてください） |
| 各停留所の時刻 | `next_text`（時刻表上の時刻）を表示します。すでに過ぎた便と、翌営業日の便は、フロントエンドが取り除きます |
| 路線カードのランプ | 本日まだ便がある場合は吹き出しと「時刻表のみ・次発 HH:MM」。ない場合は × と「本日の運行はありません」 |
| 停留所カード | `departures_text` を表示します。過ぎた便はフロントエンドが取り除きます |
| `note` | 便の注記。「※錆ヶ浜港着岸時」のように表示します |
| `active_today` | 第 7.4 節を参照 |

「営業日」は、日本時間の午前 4 時を境にします。

### 6.7 リアルタイム情報のある事業者：遅れの判定

遅れはフロントエンドで計算します。しきい値は `js/buses.js` の先頭にあります。

- 車両ごとの遅れ：`delay_minutes` を優先します。`null` の場合は、その停留所の `eta` から、最も近い時刻表上の時刻（`scheduled`、`prev`、`next`）を引いて推定します。
- 推定した値が +30 分を超える、または −5 分より早い場合は、便の対応が誤っているとみなして使いません。`delay_minutes` が −3 分より早い場合も表示しません。
- 路線全体：1 台で 10 分以上、または 2 台以上の平均が 5 分以上の場合は ×。1 台で 6 分以上、または平均が 4 分以上の場合は △。
- 運行中の車両がない場合：時刻表上の次の便があれば吹き出しと「運行中の車両なし」、なければ「本日の運行は終了しました」。

## 7. 船（東海汽船）と島しょ部のバスの連動

### 7.1 `GET /api/ship/schedule?date=YYYY-MM-DD`

ある 1 日の、全航路の便と運航状況です。フロントエンドが使う船のエンドポイントはこれだけです。

```jsonc
{
  "date": "2026-10-16",
  "is_today": true,
  "updated": {
    "effective_from": "2026-10-01", "valid_to": "2026-12-31", "expired": false
  },
  "alerts_updated_at": "2026-10-16T11:30:33+09:00",
  "alerts_error": null,
  "routes": [
    {
      "route": "東京～三宅島・御蔵島・八丈島航路",
      "trips": [
        {
          "name": "2500便",
          "ship": "さるびあ丸",
          "departure": { "port": "八丈島", "text": "09:40" },
          "arrival":   { "port": "東京・竹芝", "text": "20:55" },
          "stops": [
            { "port": "八丈島", "skipped": false },
            { "port": "御蔵島", "skipped": true },
            { "port": "三宅島", "skipped": false },
            { "port": "東京・竹芝", "skipped": false }
          ],
          "status": {
            "level": "conditional",
            "label": "条件付き運航",
            "ports": { "三宅島": "錆ヶ浜（阿古）港", "八丈島": "底土港" },
            "changes": [
              { "island": "三宅島", "from": "三池港", "to": "錆ヶ浜（阿古）港" }
            ],
            "messages": [ "（運航情報の原文）" ],
            "skipped": [],
            "url": "https://www.tokaikisen.co.jp/schedule/"
          },
          "history_key": "20261016_76043f4b03"
        }
      ]
    }
  ]
}
```

<!-- 表: /api/ship/schedule の項目 -->

| 項目 | 説明 |
|---|---|
| `date`、`is_today` | このデータの日付と、日本時間の今日かどうか。今日のページは 5 分ごとに再取得します |
| `updated` | 時刻表の改正日と有効期限。`expired: true` のときは案内を表示します |
| `alerts_updated_at` | 運航情報の更新時刻。「運航情報 11:30 更新」のように表示します |
| `alerts_error` | 運航情報の取得に失敗したときのメッセージ。`null` でない場合、一覧はそのまま表示し、上に案内を加えます |
| `error` | その日の時刻表が見つからないときだけ返します（HTTP ステータスは 200 でも 404 でも構いません）。フロントエンドは原文と公式サイトへのリンクを表示します |
| `routes[].route` | 航路名。**利用者が保存する ID は `ship:` にこの名前を付けたもの**です。変えないでください |
| `trips[]` | その航路の当日の便。出発時刻の順に並べます |
| `name`、`ship` | 便名（`null` でも構いません）と船名 |
| `departure`、`arrival` | `port`（港名）と `text`（`HH:MM`。日付をまたぐ場合は `翌 15:40`） |
| `stops[]` | 途中の寄港地。フロントエンドが使うのは `port` と `skipped`（本日は寄港しない）だけで、一部欠航のときに取り消し線で表示します |
| `status` | 運航状況。**`null` は「運航情報がない」ことを表し、欠航ではありません**（先の日付はすべて `null` です）。フロントエンドはバッジを表示しません |
| `history_key` | その便の履歴のキー。`/api/history/all` の `ship` に対応します |

`status` の項目は次のとおりです。

<!-- 表: status（船）の項目 -->

| 項目 | 説明 |
|---|---|
| `level` | 等級。第 7.2 節を参照 |
| `label` | バッジに表示する文字列 |
| `ports` | 各島の本日の着岸港。`{ "島名": "港名" }` の形式です。未定の場合の値は `未定` |
| `changes` | 港の変更。`[{ island, from, to }]` の形式で、「⚠ 三宅島：三池港 → 錆ヶ浜（阿古）港」のように表示します |
| `messages` | 運航情報の原文（文字列の配列）。折りたたんで表示します |
| `skipped` | 一部欠航のときに運航しない区間または港。例：`["新島〜神津島"]`。「一部欠航（新島〜神津島間）」のように表示します |
| `url` | 公式の運航情報の URL |

### 7.2 `level` とランプ

<!-- 表: level の値 -->

| `level` | 意味 | バッジの色 |
|---|---|---|
| `cancelled` | 欠航 | 赤 |
| `partial` | 一部欠航（1 つの便の中で一部の区間・港に寄らない） | 黄 |
| `conditional` | 条件付き運航 | 黄 |
| `changed` | 出帆港変更 | 黄 |
| `pending` | 就航判断待ち | 橙 |
| `undecided` | 出帆港未定 | 灰 |
| `normal` | 運航予定 | 緑 |
| その他の値 | フロントエンドは「運航情報あり」として扱います。平常としては扱いません | 黄 |

航路カードのランプは、当日のすべての便の `level` から、次の順で判定します。

<!-- 表: 航路カードのランプ判定 -->

| 条件 | ランプ | バッジ |
|---|---|---|
| 当日この航路に便がない | × | 運航なし |
| すべて欠航 | × と吹き出し | 全便欠航 |
| 欠航の便がある | × と吹き出し | 欠航あり |
| 一部欠航の便がある | △ と吹き出し | 一部欠航 |
| 条件付き運航の便がある | △ と吹き出し | 条件付き |
| 出帆港変更の便がある | △ と吹き出し | 出帆港変更 |
| 知らない等級の便がある | △ と吹き出し | 運航情報あり |
| 就航判断待ちの便がある | 吹き出し | 判断待ち |
| 出帆港未定の便がある | 吹き出し | 出帆港未定 |
| すべての便の `status` が `null` | 吹き出し | 情報なし |
| すべて運航予定 | 〇 | 運航予定 |

### 7.3 フロントエンド側で計算する部分

- **出航済み・到着済み**：公式の告知は出航後も「運航予定」のままです。フロントエンドは時刻表の出発・到着時刻と現在時刻を比べ、出航した便を「出航済み」、到着した便を「到着済み」と表示します。対象は、運航すると決まっている便（`normal`、`conditional`、`changed`、`partial`）だけです。リアルタイムの位置情報ではありません。
- **次の出航**：当日の便のうち、出発時刻がまだ来ておらず、欠航でもない最初の便です。
- **検索**：航路の一覧は当日の `/api/ship/schedule` から作ります。このほか、固定で書かれている会社名と島名のキーワードとも照合します。

### 7.4 船と島しょ部のバスの連動：役割分担

三宅島の船は、日によって着く港が変わります。三宅村営バスの一部の便は、船が特定の港に着く日だけ運行します。**「今日どの便が運行するか」はバックエンドが判定し、フロントエンドは表示だけを行います。**

<!-- 表: 船とバスの連動の役割分担 -->

| 作業 | 担当 |
|---|---|
| 港別の便が今日運行するかどうかの判定（`active_today`） | バックエンド |
| 停留所の「これからの発車」（`departures`。今日運行しない版は空の配列） | バックエンド |
| 今日その島に着く船の便と港の整理（`ship_link`） | バックエンド |
| 祝日の判定（`today`） | バックエンド |
| 「本日運行」「本日運休」のラベル表示、運行しない便を薄く表示 | フロントエンド |
| 運行しない便をランプと次の便の判定から除外 | フロントエンド |
| すでに過ぎた時刻表上の便を取り除く | フロントエンド |
| 船のページの着岸港 → その港のバス時刻表を開く | フロントエンド |
| バスのカードの「⛴ 本日の着岸港」→ 船のページを開く | フロントエンド |

#### バックエンドが提供する項目

`/api/bus/route` の `patterns[]`、および `/api/bus/stop` と `/api/bus/timetable` の `routes[]` に付けます。

<!-- 表: 港別の便に付ける項目 -->

| 項目 | 値 | フロントエンドの表示 |
|---|---|---|
| `note` | 例：`錆ヶ浜港着岸時`、`三池港着岸時の船連絡バス`、`登校日のみ` | 路線名の横に「※…」 |
| `active_today` | `true` | 「本日運行」のラベル |
| `active_today` | `false` | 全体を薄く表示し、「本日運休（着岸港が異なるため）」と表示。時刻は「運休」 |
| `active_today` | `null` | 港がまだ発表されていない状態。`note` だけを表示 |
| `active_today` | 項目なし | 通常の便 |

島しょ部のバス事業者の結果には、次の項目も付けます。

```jsonc
"ship_link": {
  "island": "三宅島",
  "date": "2026-10-16",
  "sailings": [
    {
      "name": "3500便", "ship": "さるびあ丸", "from": "東京・竹芝",
      "arrival_text": "05:00", "port": "錆ヶ浜（阿古）港"
    }
  ]
}
```

`port` が `null` の場合、フロントエンドは「未発表」と表示します。`date` は、同じ日付の船のページを開くために使います。

#### バックエンドの判定方法（推奨）

1. バスの時刻表では、港別の便がそれぞれ対応する港を持っています（例：三池港、伊ヶ谷港、錆ヶ浜港の 3 つの版。時刻は同じです）。
2. 当日の東海汽船の運航情報から、その島の着岸港を取得します（`/api/ship/schedule` の `status.ports["三宅島"]` と同じ情報です）。
3. 港別の版ごとに判定します。港が同じなら `true`、港が発表済みで異なるなら `false`、港がまだ発表されていなければ `null` です。
4. `active_today: false` の版は、停留所の `departures` を空の配列にします。

#### フロントエンドの「港名 → 停留所名」の対応

船のページの着岸港の横にはバスのアイコンがあり、押すとその港のバス時刻表を開きます。対応の方法は `js/ship.js` の `busStopFor` にあります。

- このリンクがあるのは大島（`OshimaBus`）と三宅島（`MiyakeVill`）だけです。
- 停留所名は、港名からかっこの中を除いたものです：`錆ヶ浜（阿古）港` → `錆ヶ浜港`。
- この停留所名で `/api/bus/timetable/{停留所名}` を呼び出し、その事業者の結果だけを表示します。

> **注意**　バスのデータの停留所名は、「港名からかっこを除いたもの」と一致させてください。

## 8. 履歴

### 8.1 `GET /api/history/all`

すべての履歴を 1 回で返します。フロントエンドは 60 秒ごとに取得し、利用者のカードにある路線の分だけを取り出します。

```jsonc
{
  "railway": {
    "odpt.Railway:JR-East.Yamanote": [
      {
        "status_text": "平常運転", "message": "平常運転",
        "update_time": "05:48", "delay_minutes": 2,
        "timestamp": 1792529352090
      }
    ]
  },
  "flight": {
    "Departure_UO625": [
      {
        "fid": ["UO625", "CX5625"], "type": "Departure",
        "status": "搭乗手続中", "note": "",
        "system_updated": "05:48:06", "timestamp": 1792529352090
      },
      {
        "fid": ["UO625", "CX5625"], "type": "Departure",
        "status": "搭乗中", "note": "【状況変更】",
        "system_updated": "05:53:16", "timestamp": 1792529654482
      }
    ],
    "Arrival_BA007": [
      {
        "fid": ["BA007", "JL7082"], "type": "Arrival", "status": "遅延",
        "note": "到着便の履歴機能はサポートされていません。",
        "system_updated": "06:24:00", "timestamp": 1792531467770
      }
    ]
  },
  "ship": {
    "20261016_76043f4b03": [
      {
        "timestamp": 1792110900000, "date": "2026-10-16",
        "name": "2000便", "ship": "さるびあ丸",
        "route": "東京・横浜～大島・利島・新島・式根島・神津島航路",
        "departure_text": "10:30",
        "arrival_time": "2026-10-16T19:00+09:00",
        "level": "normal", "label": "運航予定",
        "ports": { "大島": "岡田港" }, "changes": [],
        "tags": ["状況変更", "出帆港決定"]
      }
    ]
  }
}
```

配列はどれも古い順です。現在のバックエンドは、1 つのキーにつき最大 5 件まで保持します。フライトの各記録は、その時点のフライトのオブジェクト（第 5.1 節のすべての項目）に `timestamp` を加えたものです。上の例は、フロントエンドが使う項目だけを抜き出しています。

<!-- 表: /api/history/all の区分 -->

| 区分 | キー | フロントエンドが使う項目 |
|---|---|---|
| `railway` | 路線 ID | `status_text`、`message`、`update_time` |
| `flight` | `Departure_` または `Arrival_` に、`fid` の先頭の便名を付けたもの | `fid`、`status`、`note`、`system_updated` |
| `ship` | 便の `history_key` | `timestamp`、`date`、`name`、`ship`、`route`、`departure_text`、`arrival_time`、`label`、`ports`、`changes`、`tags` |

### 8.2 種類ごとのルール

**鉄道**：`status_text` に「平常」「通常」が含まれる場合は 1 行で表示します。それ以外の場合は `message` もあわせて表示します。

**フライト**：

- フロントエンドがキーを探す順序は次のとおりです。リアルタイムのフライト情報の `type` と `fid` の先頭からキーを組み立てる → `Departure_{便名}` → `Arrival_{便名}` → 各記録の `fid` から逆引き。このため、共同運航便名で保存したカードでも見つかります。
- 記録の `note` のすべてに「履歴機能はサポートされていません」が含まれる場合、フロントエンドはその便を履歴の対象外と判断し、「到着便は履歴の対象外です」と表示します。現在のバックエンドは、到着便についてこのように返します。
- 履歴は取得できたがその便がない場合は、「この便の履歴はありません」と表示します。

**船**：

- ある便に履歴があるかどうかは、`ship[history_key]` が空でない配列かどうかだけで判断します。`status` は見ません（出航後に公式の告知が取り下げられても、履歴は残ります）。
- カードの航路は、各キーの最後の記録の `route` と航路名を照合します。
- `tags` の値は `状況変更`、`出帆港決定`、`出帆港変更`、`案内変更` です。フロントエンドは 2 行目の説明を決めるために使います。

**バス**には履歴がありません。フロントエンドは「バス路線は履歴の対象外です」と表示します。

## 9. データ提供状況

### 9.1 `GET /api/sources`

データの提供期間が終了する前後に、案内を表示するために使います。サイトを開いたときに 1 回取得し、失敗してもほかの機能には影響しません。

```jsonc
{
  "challenge_name": "公共交通オープンデータチャレンジ",
  "challenge_end": "2027-02-28",
  "sources": [
    {
      "id": "jr_info", "label": "JR東日本 運行情報",
      "challenge": true, "state": "ok"
    },
    {
      "id": "flights_nrt_hnd", "label": "成田・羽田",
      "challenge": true, "state": "ok"
    }
  ]
}
```

フロントエンドが使うのは次の項目だけです。

<!-- 表: /api/sources の項目 -->

| 項目 | 用途 |
|---|---|
| `sources[].challenge` と `state` | `challenge: true` で `state` が `ended` の提供元があるときに案内を表示します |
| `sources[].id` | `flights_nrt_hnd` が終了した場合はフライトの案内、それ以外の提供元が終了した場合は鉄道の案内を表示します |
| `challenge_end`、`challenge_name` | 終了の 30 日前から、「通知・履歴」に残りの日数を表示します |

案内の文章は `js/data-sources.js` に固定で書かれており、具体的な事業者名が含まれています。自分のバックエンドが扱うデータの範囲が異なる場合は、この文章を書き換えてください。この機能が不要な場合は、エンドポイントが `{ "sources": [] }` を返すようにすれば十分です。

## 11. 上流データと利用条件

フロントエンドが上流のデータに直接触れることはありません。ただし、バックエンドを自分で運用する場合は、データを自分で入手し、各データの利用条件を守る必要があります。現在の本番サイトが利用しているデータは次のとおりです（サイト内の「データ元」ページと README に基づきます）。

<!-- 表: 本番サイトが利用しているデータ -->

| データ | 提供元 | 備考 |
|---|---|---|
| 鉄道の運行情報、列車ロケーション情報 | 公共交通オープンデータセンター（ODPT） | |
| JR 東日本・東武・西武・京急・京王・東急の運行情報、JR 東日本・東武の列車ロケーション情報、成田・羽田のフライト情報 | 公共交通オープンデータチャレンジ2026 の限定提供データ | 2027 年 2 月末まで提供予定 |
| 都営・横浜市営・西武のバス | ODPT | |
| 東海汽船の時刻表と運航情報 | 東海汽船 | 時刻表は GTFS |
| 大島バスの時刻表 | 大島旅客自動車 | GTFS |
| 三宅村営バスの時刻表 | 三宅村／ODPT | CC BY 4.0。出典の表示が必要です |

注意事項は次のとおりです。

- ODPT のデータを利用するには、自分で ODPT に開発者登録を行い、アクセスキーを取得する必要があります。アクセスキーはバックエンドだけに置いてください。
- サイト内の出典の表示（「データ元」ページ、時刻表と船のページの下部にある「公共交通オープンデータセンターのデータを利用しています」、三宅村営バスの CC BY 4.0 の表示）は、データの利用条件に合わせて入れているものです。ほかのデータを使う場合は、実際の提供元に合わせて書き換えてください。そのまま削除しないでください。
- 各データの利用条件は、提供元の最新の規約を確認してください。本書は規約の代わりにはなりません。

## 13. バックエンド側で補足が必要な事項

次の内容はフロントエンドからは分かりません。ほかの人が同じバックエンドを作れるようにするには、バックエンド側で補う必要があります。

- 各エンドポイントが利用する上流の API、取得の頻度、キャッシュの時間。
- CDN と CORS の設定。
- 列車ロケーション情報から遅延分数を算出する方法、方面名の決め方、直通列車（湘南新宿ライン、上野東京ライン）の集計方法。
- `internal.` で始まる路線 ID の一覧と、それらの路線のデータの提供元。
- `/api/dictionary` の `version` の生成方法。
- フライト：成田・羽田と JAL・ANA の 2 種類の提供元をどうまとめているか、ターミナルと搭乗口の提供元、`stale` の判定。
- バス：`source` に入る値、`delay_minutes` の算出方法、`occupancy` に入る値。
- 東海汽船の運航情報の取得方法と解析のルール（`level` の判定方法）。
- GTFS の取得元の URL と更新の方法。
- 祝日の判定方法。
- 履歴の保持のルール（1 件あたりの件数、消去のタイミング、船の保持時間）。
- バックエンドの環境変数（例：テスト用のデータ提供終了日）。
- バックエンドも公開するかどうか。
